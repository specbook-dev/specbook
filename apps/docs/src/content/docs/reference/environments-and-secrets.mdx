---
title: Environments and secrets
description: Where each API lives in each environment, and where credentials come from.
---

`vars` in the config are the defaults for every environment. `.specbook/environments/<env>.env` (or
`environments.<env>.vars`) overrides them for one environment, and `<env>.secrets.env`, which the folder's
`.gitignore` keeps out of the repository, holds its secrets. A service's address is a variable, so each environment
can point elsewhere:

```ts
services: { petstore: { spec: './openapi/petstore.json', baseUrl: '{{petstoreUrl}}' } }
```

```sh
# .specbook/environments/staging.env
petstoreUrl=https://staging.petstore.example/api/v3
```

## Secrets

Secrets are named in the config (`secrets: { PETSTORE_API_KEY: {} }`) and read from environment variables first, then
from `--secrets-file`, the environment's `<env>.secrets.env`, and `secrets.local.env`. `specbook secrets --env staging`
shows where each one resolves from, never its value. A test run masks every secret value wherever it appears, in its
URL-encoded, JSON-escaped and base64 forms too, and removes credentials from reports.

## In a browser

A published portal never holds a secret. A visitor types credentials once per tab, they are kept per API origin, and
a key typed for one API is never sent to another. An embed keeps them in memory only.

## Addresses on the same origin

A relative address (`/api/petstore`) is resolved against the page, so one environment file serves every host a site
is published on. This site's demo environment does exactly that.
